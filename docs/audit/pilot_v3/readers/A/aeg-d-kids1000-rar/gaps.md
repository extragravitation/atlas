# Method gaps — aeg-d-kids1000-rar/v3, rows m000003 and m000012

No step was "method incomplete" for g_obs or g_bar; both rows were computed. The following steps were inferred or resolved by judgement, even where confident.

1. **Mapping measurement_id to data row.** METHOD.md says one row of the measurements table is one data row of one ESD file, but does not say how a measurement_id (m000003, m000012) maps to a file and row. I took the mapping from rows.json (locators: KiDS file, data rows 3 and 12), not from METHOD.md. In general (all three files, 45 rows) the method gives no numbering rule.
2. **Value of M☉.** §1 gives M☉ = 1.98840987 × 10³⁰ kg but also says the constants come "through astropy ≥ 6.1", whose IAU 2015 value has more digits (1.988409870698051 × 10³⁰). The brief says to use only constants stated in the method, so I used the printed 9-digit value. The difference is about 4 × 10⁻¹¹ relative, which does not change any printed digit, but which value the code uses is not stated.
3. **Which constants, versus the README.** The release README gives its own recipe constants (G = 4.52 × 10⁻³⁰ pc³ M☉⁻¹ s⁻², pc = 3.086 × 10¹⁶ m). Those values differ from METHOD §1 by about 0.03 %. I followed METHOD §1 as instructed. The method calls step 1 "the README's recipe" but does not say that it replaces the README's numerical constants.
4. **h₇₀ handling.** §1 says ΔΣ is "in h₇₀ M☉ pc⁻², with h = 0.7, physical. It is used as released." I read this as: no factor of h₇₀ is applied (h₇₀ = 1 for H₀ = 70; the paper's l. 165 adopts H₀ = 70 km s⁻¹ Mpc⁻¹). The phrase "with h = 0.7" could be misread as an instruction to rescale, so the wording is a mild ambiguity.
5. **Reading the column-1 header.** The file header names column 1 "Radius(m/s^2)". METHOD §2 says column 1 is g_bar. The README says that for RAR files the "Radius" column is in m s⁻². I relied on METHOD and the README together. A reader with only the file would see the label "Radius".
6. **Data-row counting.** "Non-comment lines, counted from 1": I treated lines that start with '#' as comments (there is one header line), so data row k is file line k+1. The method does not define the comment character.
7. **Archive layout.** sources.json gives S2's file as `arxiv/2106.11677v1.tar.gz`. In the packet it is at `files/2106.11677v1.tar.gz`. The tar also holds macOS `._*` resource-fork members, which I ignored. The hashes matched: both archives, all seven listed members, and RAR_paper_Brouwer_4.tex.
8. **g_bar bin check (not needed for the values).** §4 gives bin edges, and rows.json says the released g_bar is the arithmetic midpoint of the bin. METHOD.md itself does not say "arithmetic midpoint". I checked: the released 4.3030e-15 and 7.1310e-13 equal the arithmetic midpoints of bins 3 and 12 (4.30296e-15 and 7.13098e-13), not the geometric midpoints (4.135e-15 and 6.853e-13).
9. **"§2.1" label.** The paper's LaTeX does not number its sections. I inferred §2.1 = `\subsection{Mass measurements with weak gravitational lensing}` (label sec:Lensing) under `\section{Theory}`, assuming that Theory is section 2. The bin text is at l. 174 as stated.
10. **Plotting rule cross-check.** The quote "by only using the seven data points within the isolation criterion limit" is at l. 508. There the limit is written as R < 3 h₇₀⁻¹ Mpc. Line 595 gives the limit as g_bar < 10⁻¹³ m s⁻², which puts rows 1–8 outside it (row 8 = 7.358e-14, row 9 = 1.298e-13). That agrees with the method's rows 9–15. The method itself relies on a fixed row list rather than a g_bar threshold.
